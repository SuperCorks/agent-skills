# Docker and local databases

## Docker Desktop

- Confirm the CLI context is the intended local Docker Desktop engine and confirm which Buildx builder belongs to it. A current context or builder can point at a remote host. Inspect `docker system df` and `docker buildx du --builder <local-builder>` for different views. Report the allocated size of Desktop's virtual disk separately. Docker's shared layers make image and cache figures overlap. An estimate marked reclaimable is not proof that the corresponding data is disposable.
- Build cache is generally the lowest-risk Docker target. For approved cleanup, use builder-scoped prune of unused cache with the chosen builder and any required age filter. Measure the builder and host disk before and after. Removing images can turn formerly shared cache into private cache; recheck if the first pass leaves materially useful reclaimable space in the approved scope. Avoid treating a virtual disk's logical size as the achieved saving.
- For unused images, inventory **all** container references, including stopped containers. Preserve user-built local-only images and aliases. Verify a matching immutable digest is accessible in its registry by inspecting the remote manifest, then recheck image identity, tags, and references immediately before deleting exact approved images without force. Keep candidates whose registry copy or use could not be verified.
- For volumes, inventory container mounts and inspect only the detached candidates. A Docker “unused” volume can contain the only copy of a database, environment configuration, or a nested Docker engine. Inspect contents read-only if metadata is insufficient, preferably through a local image, with a read-only mount. Remove only individually verified disposable caches, known empty stores, or expressly approved data volumes. Check that protected volumes still exist afterward. Avoid broad system/volume prunes and leave `Docker.raw` itself to Docker Desktop.

## Local databases and durable streams

- Treat SQLite, WAL, and other local data as persistent state even if found under a cache-looking name or a stopped process. For example, Prisma dev can retain a large `~/Library/Application Support/prisma-dev-nodejs/durable-streams` tree separate from package caches.
- Inspect storage size, recent write timestamps, process references, and lifecycle metadata from the installed tool. For SQLite, use read-only catalog queries for retention/expiry and aggregate counts when appropriate, rather than dumping application payloads. An immutable SQLite connection can miss uncheckpointed WAL state; do not rely on that view to certify a store as disposable. Old timestamps, no open handles, or a detached Docker volume are insufficient evidence of disposability.
- Only propose confirmed disposable stores for cleanup. If the app has a targeted supported cleanup command, verify its locally installed help and exact scope before using it with authorization. Do not unlink SQLite WALs to reclaim space or wipe the entire directory when stream ownership or expiry is uncertain.
