# Cleanup targets

## Development output and dependencies

- Scan both primary and secondary checkouts. Common high-value paths include project `.next`, Turborepo `.turbo/cache`, Cargo `target`, Android `app/build/intermediates`, iOS build directories, and custom test output such as `.e2e-build`. Verify the project/tool structure instead of deleting by a generic name like `build`, `dist`, or `tmp`. Within mixed folders, isolate reproducible directories such as Xcode `Build` and `ModuleCache.noindex`. Separate Android packages, test results, logs, fixtures, emulator disks, and exports when their provenance or value is uncertain.
- In repositories, check exact paths with `git ls-files -- <relative-path>` and, when useful, `git check-ignore`. Ignored assets can be the only copy. Imported media, datasets, catalog databases, and local backups need separate, explicit scope. A source or test process may be using the artifacts even if the last Git commit is old.
- Installed `node_modules`, Python environments identified by `pyvenv.cfg`, and CocoaPods output can be cleanup candidates when the project's manifests and toolchain can recreate them. Look for local modifications or bundled data where relevant. Preserve package lockfiles and project settings such as Bundler `.bundle/config` and Expo device settings. Prefer package-manager cleanup for shared stores, and check the actual npm/pnpm/Gradle/uv/CocoaPods/Homebrew cache location and active tool versions. A Gradle daemon can hold shared caches open. Distinguish those from older unused cache versions. Expect regeneration and redownloads.
- Project age checks should include source writes, Git activity, and, when relevant, newer builds. Use a clear cutoff in the user's timezone. Group a primary checkout with its linked worktrees, and check for another local clone of the same project before calling the whole project inactive. Older copies of active projects can be a separate option. Absence of writes does not prove absence of use.

## Xcode and simulators

- `~/Library/Developer/Xcode/DerivedData` can refill quickly. Measure individual idle project folders and the module cache. Check open files and running builds/tests, including custom `-derivedDataPath` and `-xctestrun` targets. Keep archives, signing data, source packages with local edits, and device state out of a generic build-cache batch.
- Use `xcrun simctl list devices --json` to compare availability, boot state, last boot and data size. Use `xcrun simctl runtime list` to map installed runtimes. A shutdown simulator may still be a recent test fixture or contain useful app data. After approval, use `simctl` for exact devices or confirmed unused runtimes. With physical device support files, retain versions still needed for debugging. Avoid summing mounted runtime sizes with the backing disk.

## Personal files and app caches

- Separate browser caches under `~/Library/Caches` from profiles under Application Support, local storage, cookies, sessions, passwords and bookmarks. Clear only the approved cache paths. A browser can repopulate them while open; measure again and report regeneration rather than repeatedly deleting new files. For UI-based work, follow the user's browser instructions. Large code-signing clone folders under `/private/var/folders` may be mostly shared blocks; never treat their folder size as automatic savings.
- For Downloads, apply whatever cutoff the user approved, using local calendar dates. Creation and modification timestamps together are safer than either alone. Check descendants before selecting a whole folder. Keep folders with newer contents unless an approved file-level pass can isolate old entries. Clear storage intentionally; moving to Trash typically keeps the bytes on the same disk until emptied, and emptying the rest of Trash is a separate action.
- Distinguish downloadable model caches from local models, fine-tunes, and active runtimes. Identify what is installed and in use before clearing a model cache. Downloads can be large and may require network access or credentials again.
